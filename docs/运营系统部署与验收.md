# 童印 · 单体运营系统部署与验收

> 本文对应同一仓库中的 Go 单体、小程序原生客户端和嵌入式 HTML 管理后台。无需部署第二个 Web 后端、Node 服务、Java 或微服务。

## 一、最终架构

- **一个 Go 进程、一个监听端口**，提供 `/api/`、`/media/`、`/admin/`。
- 运营后台已编译嵌入 `backend/webadmin/index.html`（`go:embed`），更新 Go 可执行文件即更新后台。仓库 `admin/index.html` 保留相同源码用于开发。
- 继续使用原有 PostgreSQL（或设置 `DB_DRIVER=mysql` 换 MySQL），增加 `ty_users`、`ty_admins`、`ty_audit` 三个表。保留旧表与旧作品/订单数据；启动时根据历史作品及订单补齐用户档案，不会改动其 OpenID 所有权。
- 微信小程序由微信平台发布，不是服务器的第二个进程。使用同一 Go API。公网正式版需要已备案域名、有效 HTTPS 证书、微信 request/upload 合法域名。

## 二、首次升级

1. **先备份**生产数据库以及 `backend/data/media/`，不要仅备份代码。不可把用户收货地址或微信 OpenID 上传到 GitHub。
2. 更新仓库：`git pull origin main`。更新 `backend/.env` 的密码及快递配置，继续保留原来的数据库 DSN 和 `SESSION_SECRET`（不能随意更换；更换会导致所有已签发会话、图片签名失效）。
3. 设置：
   ```env
   ADMIN_BOOTSTRAP_USER=admin
   ADMIN_BOOTSTRAP_PASSWORD=<使用自己生成的至少12位强密码>
   # 旧版 ADMIN_TOKEN 可保留作应急入口；不需要时建议置空。
   KUAIDI100_KEY=
   KUAIDI100_CUSTOMER=
   ```
4. 重新启动 Go：Windows 开发仍执行 `.\scripts\dev.ps1`；真机开发同局域网用 `.\scripts\dev.ps1 -Phone`。
5. 访问 `http://localhost:18080/admin/`，输入后台管理员账号和密码。首次启动只在账号不存在时创建初始管理员；之后重启不会覆盖管理员手动修改的密码。
6. 生产部署时只需一个 Go 可执行文件 + 配置、数据库、媒资数据卷。运营后台首页已打入 Go 二进制；无需 Nginx 以外的第二个业务进程。Nginx 可作为 TLS 入口反向代理到 Go。

## 三、权限与微信用户

- 小程序 `wx.login()` → Go `/api/auth/wechat` → 微信 `code2session` → OpenID → 独立用户档案和签名登录令牌；`GET /api/me` 可查看自己的内部用户 ID、作品数、订单数。
- **不要在真机多用户验收时开启 `DEV_LOGIN`**。该选项会把所有设备视为同一测试账号 `dev-user`；需要关闭开发登录并配置真实微信 AppID/Secret、可访问的 HTTPS 服务。
- 所有作品、订单和地址数据仍按认证后的 OpenID 在 Go 服务端过滤；管理后台列表显示内部用户编号，不展示 OpenID。
- 后台角色：`owner` 全部权限；`operator` 作品+订单；`production` 模型制作；`shipping` 发货与物流；`service` 只读客服查询。初始管理员可创建账号、修改角色或密码、停用管理员。更改管理员账号后会使旧会话失效。
- 旧版 `ADMIN_TOKEN` 应急密钥仅用于过渡或恢复操作，持有它的人具有最高后台权限，请使用强随机值并严格保护。
- 用户信息包含收货人姓名、电话、地址，发布前需要完成小程序隐私保护指引、数据留存/删除制度和生产数据库备份策略。

## 四、订单、物流和退款

订单：待付款 → 已支付 → 制作中 → 已发货 → 已完成；不可跳状态。只有待付款且**尚未发起微信支付**的订单允许用户自行取消。已发起预支付请求的订单需先核对商户侧支付状态，避免“取消订单后仍实际扣款”。微信支付状态只能由正确的支付回调在验签、解密、金额和 OpenID 校验后变更，不可在后台直接标记已付款。如果已经取消的旧订单之后收到微信支付成功回调，系统会记录实际付款并标记为待人工退款核对，而不是忽略这笔交易。

物流后台：
1. 订单付款成功后点击「开始制作」。
2. 制作完成后填写真实的快递公司、**快递100公司的英文编码**（例如 `shunfeng`）和运单号，再确认发货。
3. **不配置快递100凭证**时，用户可以看到物流公司、运单号，但不会出现伪造的运送轨迹；运营人员可从快递官网核实后补录，标记来源为「人工」。
4. 配置 `KUAIDI100_KEY` 和 `KUAIDI100_CUSTOMER` 后，后台可执行「查询物流」，数据直接来自快递100实时查询 API，每单限制至少30分钟查询一次。查询可能扣除快递平台额度，正式启用前请确认合同与费用。
5. 物流轨迹缓存到原订单记录，小程序访问 `GET /api/orders/{id}/tracking` 查看；用户无权限查看他人运单，且不会因重复打开页面而高频扣费。收到签收数据会记录已签收物流状态，订单完成仍由运营方确认。
6. 系统提供「退款申请记录」但**不会在没有完成商户退款对接的情况下宣称已退款**。真正退款资金操作需通过微信支付商户平台或后续正式接入的退款接口完成；不能凭修改字段代替资金退回。

## 五、上线验收

- [ ] 两个实际微信账号分别上传原画、选择形象图、查看 GLB，不能互相访问作品详情。
- [ ] A 用户下单、保存地址、退出重进，地址还在；B 用户看不到 A 的订单/地址。
- [ ] 待付款订单重进时显示「继续付款」而不是重复下单；该状态允许修改地址，历史订单地址快照不变。尚未发起支付时可以取消，已经发起支付时无法直接取消。
- [ ] 管理后台建立制作人员账号，其无权创建管理员和操作用户状态。
- [ ] 后台原画 → 形象图 → GLB 上传流程与原有小程序 3D 交互预览不回归。
- [ ] 只有支付通知验签通过才改变付款状态；真实商户参数与回调必须经过实机验收。
- [ ] 订单从支付 → 制作 → 发货，输入真实运单号；小程序展示运单号、物流轨迹；未开通快递100时明确展示「暂无轨迹」。
- [ ] 运营后台停用用户后，小程序下次请求失败；账号重启后的用户、地址、作品、订单和物流仍存在。
- [ ] 所有订单状态与敏感后台操作能通过管理员的操作审计查看。
- [ ] 完成数据库和媒资备份/恢复演练，验证正式 HTTPS 域名和微信小程序的实际授权配置。
